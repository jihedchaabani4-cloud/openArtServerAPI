# Report: D3 — Verifications (Phase P1)

## 1. D3(1): Memory Fallbacks Outside Tests Prohibition

### Findings & Evidence
1. **Default value of `useMemoryFallback`**: `RunRepository.useMemoryFallback` was initialized to `false` (`src/v2/runner/runRepository.js:20`).
2. **Who sets it**: In `src/v2/runner/runRepository.js:108,117`, a `catch` block on database error `PGRST205` previously assigned `RunRepository.useMemoryFallback = true` dynamically at runtime, logging a `console.warn`.
3. **DB error propagation**: In production or development, database errors on `v2_workflow_runs` must never silently switch storage to RAM. A constructor was added to `RunRepository` that explicitly throws if fallback is requested outside `NODE_ENV=test`. In `createRun` and all read/update methods, `PGRST205` now logs fatal via structured logger and rethrows immediately in non-test mode.
4. **Supabase Client Fallback**: In `lib/supabase.js`, missing `SUPABASE_URL` or `SUPABASE_KEY` previously emitted `console.warn`. It has been hardened to throw a fatal startup Error (`Fatal: Supabase URL or Key is missing in environment variables.`) whenever `NODE_ENV !== "test"`.

### Verification Suite
- Suite: `tests/boundary/memoryFallbackProhibitionBoundary.test.js` (6/6 PASS)
  - `TEST 1: NODE_ENV=production, repository constructed with fallback enabled -> constructor throws` [VERIFIED]
  - `TEST 2: NODE_ENV=development, repository constructed with fallback enabled -> constructor throws` [VERIFIED]
  - `TEST 3: NODE_ENV=production, DB call rejects -> error propagates and repository did NOT switch to memory` [VERIFIED]
  - `TEST 4: NODE_ENV=test, fallback enabled -> works as before (regression guard)` [VERIFIED]

## 2. D3(2): LLM Price and Credit Arithmetic

### Execution Results with Real Manifests
Executed `calculateWorkflowBillingPlan` with registered use-cases and live manifest pricing configurations:

| use case | model | manifest cost (value + unit) | plan total | value passed to hold_credits | JS type | rounding applied |
|---|---|---|---|---|---|---|
| `image-generation-v1` | `nanobana_2` + `gemini-3.1-flash-lite` | `nanobana_2`: 8 credits; `gemini-3.1-flash-lite`: 1 credit | 9 credits | 9 credits | `number` (integer) | `Math.ceil()` |
| `video-generation-v1` | `seedance_2_5` + `gemini-3.1-flash-lite` | `seedance_2_5`: 40 credits; `gemini-3.1-flash-lite`: 1 credit | 41 credits | 41 credits | `number` (integer) | `Math.ceil()` |
| `character-sheet-v1` | `gpt-image-2` + `gemini-3.1-flash-lite` | `gpt-image-2`: 8 credits; `gemini-3.1-flash-lite`: 1 credit | 9 credits | 9 credits | `number` (integer) | `Math.ceil()` |

### Answers to Arithmetic Questions
1. **Integer vs Decimal**: All values passed to `hold_credits` are strictly integers.
2. **Rounding Rule**: `src/use-cases/workflowBillingPlan.js:129` applies `const credits = Math.ceil(rawCost)`. Each node amount is ceiled to whole credits, preventing credit loss or fractional mismatch.
3. **Reconciliation (0.05 vs 1 credit)**: An early review document (`docs/release/wip-review.md`) casually cited 0.05 credits based on raw third-party token pricing. However, the active production manifest `src/models/manifests/gemini_3_1_flash_lite/model.json` sets `"retailPricing": { "table": { "default": 1 } }`. Furthermore, `workflowBillingPlan.js` applies `Math.ceil()`, enforcing a 1-credit minimum charge.
4. **Database Column Type**: In PostgreSQL (`src/platform/billing/WalletService.js:885,894,901`), `p_amount` and `v_balance` are typed as `NUMERIC`. `NUMERIC` provides arbitrary-precision exact fixed-point arithmetic without floating point drift (`0.1 + 0.2`). Holds and deductions use whole integer credits.
